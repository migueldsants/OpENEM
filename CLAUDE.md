# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

OpENEM is a free, open-source platform to help students prepare for the ENEM (Brazilian national exam): commented questions, realistic mock exams, and performance-tracking tools.

**Phases 0–3 are implemented (API + UI):**

- **Phase 0 (foundation):** NestJS API with Prisma (PostgreSQL since Oct/2026; it started on SQLite), JWT auth (`auth` + `users` modules), `/health`, Swagger, the full MVP Prisma schema, a React+Vite+Tailwind PWA (`openem_frontend/`), Docker Compose, and a GitHub Actions CI pipeline.
- **Phase 1 (MVP):** domain modules `subjects`, `questions`, `answers`, `simulations`, `performance`, and `review` (SM-2 spaced repetition in `common/spaced-repetition.ts`). The frontend ships the full MVP UI (Home, Questões with question player + XP feedback, Simulados with timer/result, Desempenho with SVG chart, Revisão).
- **Phase 2 (post-MVP):** `favorites`, `study-plan` (weekly schedule the student builds block by block; the automatic generator was removed), `essays` (per-competency rubric grading, `common/essay-score.ts`), IRT/TRI scoring of simulations (`common/irt.ts`, populated only when questions carry calibration params `discrimination`/`irtDifficulty`/`guessing`), and a `focusMode` profile flag. Frontend screens: Cronograma, Favoritos (the essay screen was removed; see **Ferramentas** below).
- **Phase 3 (implemented):** `gamification` — **XP & levels** (quadratic curve), **leagues** (Bronze→Diamond), daily **streak** with a **combo multiplier**, a **daily login bonus**, and achievements (all pure logic + achievement/league catalog in `common/gamification.ts`, models `GamificationStat`/`UserAchievement`). XP is `GamificationStat.points` (level/league/progress are **derived** — no extra columns). Awarded when answering questions (`POST /answers` returns a rich `gamification` delta: `xpGained`/`breakdown`/`level`/`leveledUp`/`league`/`newAchievements`) and gated by the `gamificationEnabled` profile flag. Exposed via `GET /gamification/me` and `GET /gamification/achievements`. The frontend ships a **Progresso** screen (XP bar, league, streak, achievements), a Home widget, XP feedback on answering (`src/pages/Questoes.tsx`), and a profile toggle. **O dia é o de Brasília** (`src/common/study-day.ts`, fuso `America/Sao_Paulo`): sequência, chave `DailyChallengeLog.day`, XP por dia do histórico e a semana das metas semanais; em UTC o dia virava às 21h. `lastActivityOn` e `WeeklyGoal.weekStart` guardam o dia como 00:00 UTC da data (rótulo, `dayLabelDate`), e o instante em que o dia começa é `startOfStudyDay`. A migração `dia_de_brasilia` rechaveou os dados antigos. O toggle `gamificationEnabled` vale para tudo: `/gamification/achievements` e `/gamification/leaderboard` respondem `{ enabled: false }`, e quem desligou some do ranking dos outros. O ranking traz `rank` (posição real, também fora do top; desempate por `userId`, `src/common/leaderboard.ts`) e `isMe`. Todo XP creditado gera `XpLog` (o resgate do desafio também), para o gráfico fechar com o total. Conquista com `retired: true` (as de redação, sem tela no app) não é mais concedida e sai do catálogo e do total, mas quem já tem continua vendo (`visibleAchievements`). Os minutos das metas semanais somam os blocos concluídos do cronograma no dia em que estão (início do plano + `dayIndex`) e o Pomodoro (`src/common/weekly-goal-minutes.ts`).

The Phase 1 UI is fully implemented (Home, Questões, Simulados, Desempenho, Revisão) — including an **onboarding** screen (`src/pages/Onboarding.tsx`) that collects goal + minutes/day on first login (the `Profile.onboarded` flag gates the main app until completed).

Phase 3 also adds: a **daily challenge** (deterministic per-day goal, `common/daily-challenge.ts`, claimed reward in `DailyChallengeLog`, exposed via `GET /gamification/daily-challenge` + `POST .../claim`), a **recommendation engine** (`recommendation` module + `common/recommendation.ts`, `GET /recommendation/next` — weak-topic questions from recent errors), **community/forum** (`community` module, `ForumThread`/`ForumPost`, threads + replies; replies are paginated by a `createdAt`+`id` cursor (`src/community/posts-page.ts`): `GET /community/threads/:id` brings the first page, the total `replies` and `nextCursor`, `GET .../:id/posts?cursor=` the next ones (at most 50), and `POST .../:id/posts` returns only the new reply — on the Comunidade screen a reply sent before the last page is loaded waits below "Carregar mais", `src/lib/forum-thread.ts`). **AI essay correction was removed** (Oct/2026): no `ai-evaluation`/`ai-available` routes, no `common/essay-ai/`, no `ESSAY_AI_PROVIDER`/`AI_ESSAY_DAILY_LIMIT`; the corrector lives in the separate `AI-Skill-Corretor-Redacao-ENEM` repo listed on Ferramentas. `EssayEvaluation.competencyFeedback`/`annotations` stay in the schema only so old AI evaluations still load. Frontend: **Comunidade** screen, daily-challenge card + "Recomendado para você" on Home.

**Ferramentas (`/ferramentas`):** substituiu a tela de Redação. É uma lista de repositórios abertos no GitHub que complementam o OpENEM (o corretor de redação vive no `AI-Skill-Corretor-Redacao-ENEM`, como skill para agentes de IA); a lista fica no backend, em `src/tools/tools-catalog.ts`, e `GET /tools` a devolve com a contagem de estrelas. As estrelas são buscadas **pelo servidor** (`src/tools/github-stars.ts`), não pelo navegador: o CSP só libera a própria origem e o GitHub não precisa do IP do aluno. A chamada é anônima, sem token (um teste trava os cabeçalhos), então nenhuma credencial vaza. O cache dura 1 hora, renova em segundo plano e, se o GitHub falhar, mantém o último valor e tenta de novo em 5 minutos; sem valor, a tela omite a contagem. O catálogo também é a lista do que o servidor aceita consultar, então a rota não vira proxy para qualquer repositório. Cada cartão tem um botão no formato do GitHub, **Estrela | 27**: "Estrela" abre o repositório numa aba nova (o GitHub não aceita dar estrela por link) e o número leva a `/stargazers`. O módulo `essays` do backend continua, mas o app não tem mais tela para ele.

**Simulados (fase atual):** o simulado personalizado é montado **por tema** — área, matéria e assunto se **somam** (união), nunca se cruzam (`src/common/simulation-filters.ts`, puro e testado); cruzar devolvia vazio porque a maior parte do banco oficial não tem assunto. `POST /simulations` aceita template e/ou filtros (`subjectAreaIds`/`subjectIds`/`topicIds`, `examSlugs`, `yearFrom`/`yearTo`, `difficulty`, `unseenOnly`/`wrongOnly`/`onlyFavorites`, `questionCount`, `timeLimitMin`, `pareto`) e `POST /simulations/preview` devolve a contagem do recorte antes de iniciar. O aluno salva recortes como `SimulationTemplate` com `scope: 'CUSTOM'` + `ownerId` + `filters` (JSON); apagar um que já foi feito **arquiva** em vez de excluir, para não derrubar o histórico. O idioma da língua estrangeira vem do perfil quando não é informado. O `start` grava as questões sorteadas em `SimulationQuestion` e o `finish` corrige **só essas** (`src/common/simulation-answers.ts`): questão de fora é descartada e questão não entregue conta em branco — o gabarito é público, então aceitar questão de fora inflava nota, XP e ranking. Simulados anteriores à tabela não têm linhas nela e seguem corrigidos pelo que foi entregue.

**Caderno em PDF:** `POST /simulations/pdf` (por filtros/template) e `POST /simulations/:id/pdf` (de um simulado já feito) devolvem um PDF no padrão ENEM — duas colunas com fluxo real entre colunas/páginas, capa com a marca e a descrição do OpENEM, cartão-resposta, gabarito e comentários opcionais, em qualquer um dos temas de cor do app (`GET /simulations/pdf-themes`) ou numa cor livre (`brandColor`). O desenho vive em `src/common/pdf/` (PDFKit): `simulado-pdf.ts` (layout), `markdown-blocks.ts` (Markdown → blocos, puro e testado) e `themes.ts` (paletas). Imagens saem de `ENEM_MEDIA_DIR`, e só de lá — `resolveImagePath` recusa caminho fora da pasta e formato que o PDFKit não embute. **Todo PDF (simulado e fórmulas) passa pela fila `PdfRenderService`** (`pdf-runner.ts` + `pdf.worker.ts`): o desenho é CPU síncrona (o caderno de fórmulas padrão leva ~6 s) e, na thread principal, parava a API inteira. Cada PDF roda numa worker thread (só existe no build compilado; nos testes, que rodam o TypeScript, o desenho cai na própria thread), no máximo `PDF_CONCURRENCY` por vez, com `PDF_MAX_QUEUE` esperando (além disso, 503 na hora) e `PDF_TIMEOUT_MS`. As rotas de PDF têm `@Throttle(PDF_THROTTLE)` (10/min). Não chame `simuladoPdfBuffer`/`formulasPdfBuffer` direto de um serviço.

**Quadro da sala (simulado no papel):** card "Prova no papel" na tela de Simulados (`openem_frontend/src/components/QuadroProva.tsx`), para quem imprime o caderno. Abre uma lousa em tela cheia com início, término e as marcas de tempo restante, que são apagadas a cada intervalo (15, 30 ou 60 min) — entre duas atualizações a marca fica parada, como na sala, e o relógio exato só aparece se o aluno pedir. A lógica é pura e testada em `src/lib/quadro-prova.ts`; a sessão fica só no `localStorage` (`openem.quadro-prova`), sem backend, e as cores da lousa são fixas, fora dos temas. As regras de saída do ENEM (2h depois do início; caderno nos últimos 30 min) só aparecem em prova de 3h ou mais.

**Redações (`/redacoes`):** todos os temas oficiais de redação do ENEM, de 1998 a 2025 (regular, PPL/reaplicação e as demais aplicações), com a proposta, os textos motivadores e o fac-símile da página. O catálogo é **estático e versionado**: `openem_frontend/src/data/redacoes.json` (carregado em chunk à parte) e as figuras em `openem_frontend/public/redacoes/`; não há backend nem relação com o módulo `essays`. Tudo é gerado por `tools/enem-fix/redacao/` a partir dos cadernos do INEP (PDFs fora do git). **São documentos oficiais de prova: o texto é reproduzido, nunca reescrito** — nada de corrigir, resumir ou inventar rótulo, e a grafia do tema é a do caderno; as letras de música entram inteiras, como no caderno, e o que foge da transcrição (2008 sem frase-tema; texto que o PDF só tem como imagem ou em fonte ilegível, que entra como figura recortada) está marcado no dado e avisado na tela. Na tela, a página do caderno vem primeiro e a transcrição depois, com o negrito e o itálico do PDF (`partes`). Não edite o JSON à mão: mexa no roteiro, rode `montar.mjs` e depois `verificar.mjs`, que relê cada página com um segundo extrator e tem de fechar com 0 divergências (ver `tools/enem-fix/redacao/README.md`). `src/data/redacoes.test.ts` trava a estrutura.

**Tabela periódica (`/tabela-periodica`, issue #93):** os 118 elementos na grade da IUPAC (18 grupos, séries f embaixo com o marcador no grupo 3), sem backend. O catálogo é **estático e gerado**: `openem_frontend/src/data/elementos.json` (chunk à parte, no precache do service worker) sai de `tools/tabela-periodica/` (`baixar.mjs` → `montar.mjs` → `verificar.mjs`, que confere cada campo contra uma segunda fonte e tem de fechar com 0 divergências não explicadas; as explicadas ficam em `divergencias.json`). **Não edite o JSON à mão.** Cada campo grava a fonte (`fontes`), e a ficha mostra o link: massas da CIAAW 2024 (Gd, Lu e Zr revisados), configuração e energia de ionização do NIST, isótopos do NIST e da IAEA, o resto do PubChem e do mendeleev (MIT). Desconhecido é `null` ("desconhecido" e hachura no mapa de calor); estimado e previsto vêm marcados. Os textos de química (`quimica.json`) são do projeto, só propriedades químicas. Lógica pura e testada em `src/lib/`: `elementos.ts` (busca sem acento, filtros, navegação da grade, formatação), `configuracao-eletronica.ts` (Pauling, abreviada, camadas, exceções ao Aufbau, íons tirando da camada mais externa, passo a passo), `massa-molar.ts` (parênteses e hidratos) e `propriedades-periodicas.ts` (estado na temperatura, escala do mapa de calor, tendências, tom da casa). As cores são tokens `--tp-*` em `index.css` (um tom por categoria e sete degraus do mapa de calor, misturados à `--surface`); todo texto da casa fica em `--fg` e `tabela-periodica-tokens.test.ts` cobra ≥ 4,5:1 em todos os temas. A ficha abre por `?z=` (o voltar fecha). Teclado no padrão de grid do ARIA; no celular, abre na lista.

**Cronômetros e timers (`/cronometros`):** relógios avulsos, vários ao mesmo tempo, **sem relação com o Pomodoro** — não viram sessão de foco, minutos de estudo nem XP, e não há backend. A lógica pura fica em `src/lib/relogios.ts` (tempo derivado de instantes, nunca de contador), a lista num store fora do React (`src/relogios.ts`, `localStorage` `openem.relogios`, sincroniza entre abas) e a tela em `src/pages/Cronometros.tsx`. `<TimerAlarme />`, montado no App, toca o fim do timer em qualquer tela com um único timeout agendado para o próximo fim. Limites: 12 relógios, 99 voltas, timer de 1 s a 24 h.

**Desempenho semana a semana (`/desempenho`, issue #90):** a tela abre na semana atual (segunda a domingo) contra a meta do perfil (`Profile.minutesPerDay` × 7): a faixa dos 7 dias, minutos de foco do Pomodoro, questões e acerto, acerto por área (mat/nat/hum/lin; Redação conta em Linguagens), até 3 prioridades do último mês com "Praticar" (`/questoes?topicId=`) e os dias seguidos; embaixo, as semanas anteriores com a variação em pontos e o mapa de assuntos ("Todos os assuntos", sob demanda). Dados de `GET /performance/weeks?weeks=1..12`, montados por `src/common/weekly-performance.ts` (puro e testado), que conta **dia e semana no fuso `America/Sao_Paulo`** com os mesmos helpers da gamificação (`src/common/study-day.ts`). Prioridade = erro × confiança (volume) × `Topic.weight`, com mínimo de 2 respostas; respostas sem assunto ficam fora e a tela diz quantas. Progresso (`/progresso`) continua sendo a tela da gamificação. Duas correções do mesmo trabalho: `computeNextReview` limita o intervalo a `MAX_INTERVAL_DAYS` (365) — sem teto a data ficava inválida por volta do 16º acerto seguido e `POST /answers` dava 500 —, e `getSummary`/progresso de conquistas usam `activeStreak`, que zera a sequência gravada quando a última atividade foi antes de ontem.

**Caderno de fórmulas em PDF:** `POST /formulas/pdf` (filtros `formulaIds`/`subjectIds`/`topicIds`/`onlyFavorites`, que se combinam) gera capa, sumário e um cartão por fórmula em grade de linhas — os dois cartões de cada linha têm as faixas internas alinhadas. A fórmula é desenhada como vetor a partir do LaTeX: `src/common/pdf/math-svg.ts` (MathJax → SVG, puro e testado) + `svg-to-pdfkit`, com a fonte Inter embutida do pacote `inter-ui` (WOFF, não WOFF2: o fontkit quebra ao recortar a Inter do WOFF2). O MathJax liga só os pacotes de `TEX_PACKAGES` (nada de `AllPackages`: a fórmula personalizada vem do aluno), o SVG sai sem elementos de imagem (`semImagens`) e o `svg-to-pdfkit` recebe `SVG_TO_PDF_OPTIONS`, cujo `imageCallback` troca qualquer imagem por um pixel embutido. Entrada que faz o MathJax lançar exceção vira um "?" marcado como erro. A fonte do MathJax não tem letras acentuadas: `normalizeLatex` troca por acentos do TeX (textmacros) e monta a cedilha com glifos do próprio MathJax. No catálogo (`prisma/seed-formulas-lib.ts`), palavra em subscrito vai em `\text{}` e nunca use `\c{}`/`\acute{}` em modo matemático (viram erro vermelho no KaTeX do site); cada entrada é uma fórmula só, e `formerTitle` renomeia o registro antigo no seed em vez de criar outro (preserva favoritos). A fórmula personalizada tem dono (`Formula.ownerId`) e só aparece para ele — o catálogo (`isBuiltIn`) aparece para todos; o título é único por dono (`@@unique([ownerId, title])`), então o seed procura o catálogo por `title` + `ownerId: null` + `isBuiltIn`, nunca só por `title`.

**Temas de cor (tela Temas, `/temas`):** toda família tem `-light` e `-dark`, e os valores vivem em `openem_frontend/src/themes.css` (importado pelo `index.css`). Família nova mexe em **3 lugares**: o bloco no `themes.css`, `FAMILIES` (com `group`: clássicos, criativos, OLED ou acessibilidade) em `src/theme.tsx` e a lista `families` do script de boot em `public/theme-boot.js` (arquivo, não script inline: a CSP do nginx só aceita script da própria origem). `theme-boot.test.ts` e `theme-palettes.test.ts` seguram os três, e o segundo cobra contraste: `fg` ≥ 7:1, `muted` ≥ 4,5:1, `brand-ink` ≥ 4,5:1 e as cores de área ≥ 4,5:1 sobre as superfícies. O `default` (vermelho) não se mexe. Os seletores `[data-theme=…]` valem em qualquer elemento: a galeria mostra prévias com `<div data-theme>`. Os efeitos dos criativos são tokens (`--radius-*`, `--font-display`) mais o brilho/scanlines em `themes.css`, que somem com `html[data-fx='off']` e com `prefers-contrast: more`. O personalizado é v2 no `localStorage` (`{ v: 2, id?, name, light, dark }`, tema `custom-light`/`custom-dark`); o formato antigo, de um lado só, é migrado ao ler. A geração de paleta fica em `src/lib/theme-derive.ts`, sobre `src/lib/color.ts` (OKLCH + contraste WCAG). No backend, o módulo `themes` (`UserTheme` + `UserThemeLike`) guarda os temas do aluno: publicação opcional, uma curtida por aluno (toggle), sem curtir o próprio tema, e tema de outro aluno responde 404. As cores são **só `#rrggbb`** (`src/common/theme-tokens.ts`), porque vão para `style.setProperty` no navegador de outros alunos, e o frontend revalida antes de aplicar. As paletas de PDF (`src/common/pdf/themes.ts`) não acompanham as famílias novas; um tema desconhecido cai no `default`.

**Catálogo de flashcards:** os decks públicos vivem em `prisma/seed-flashcards-data.json` (área → matéria → subtema, como na tela) e entram com `npm run db:seed:flashcards`, que **sincroniza** em vez de só criar: o deck do catálogo é achado por `userId: null` + `subject` + `title` (ou `formerTitle`, que renomeia sem duplicar), e os cards são casados pela **posição** (`src/common/flashcard-seed.ts`, puro e testado) — corrigir o texto de um card mantém o id e o progresso SM-2 do aluno; card novo vai para o fim do deck. `src/flashcards/seed-flashcards-data.spec.ts` trava estrutura (área, ícone, peso, ≥5 cards, sem frente repetida) e `openem_frontend/src/components/Markdown.seed.test.tsx` renderiza todos os cards com o `<Markdown>` do app. Moeda: fora de fórmula escreva `R\$`; dentro, `\text{R\textdollar{} }` — `R$` solto e `\$` dentro de `$…$` fazem o remark-math abrir/fechar fórmula no lugar errado. Em Humanas e nos temas sociais de Linguagens, conceito controverso é **atribuído ao autor** e debate público aparece com as posições em disputa, sem o card tomar lado.

**Classificação de assunto:** duas etapas. `npm run db:classify:keywords` (`prisma/classify-heuristic.ts` + `src/common/classification/heuristic.ts`) é determinístico, roda sem chave de IA e classifica ~1/3 do banco; ele **se cala** quando dois assuntos empatam, porque assunto errado contamina revisão, recomendação e desempenho. O que sobra vem do **catálogo de assuntos** (`npm run db:classify:catalog`, `prisma/classify-catalog.ts` + `src/common/classification/catalog.ts`): `prisma/classificacao-assuntos.json`, classificação feita uma vez pelo Claude Haiku 5.5 e versionada (por `externalId`, rótulo "Matéria / Assunto" + confiança) — **não oficial**. Ele só preenche questão sem assunto, ignora confiança < 0,6, assunto que não existe mais na taxonomia e assunto de outra área; roda no bootstrap logo depois das palavras-chave e precisa ser copiado no `build:scripts`. Com as duas etapas o banco inteiro tem assunto, menos `enem:2016:165`, de enunciado truncado no dataset. Questão nova (prova importada depois) segue para `npm run db:classify` (IA). A origem fica em `Question.classificationSource` (`keywords` | `catalogo:claude-haiku` | `ai:<provedor>`).

**Official ENEM question bank:** `prisma/import-enem.ts` (+ `-lib.ts`) imports the static dataset of the `enem-api` fork (26 exams, ~4k questions) — the dataset is downloaded to a git-ignored folder, never committed (it is GPL-2.0; this repo is AGPL-3.0). Pure mapping lives in `src/common/enem-import/mapping.ts` (Jest's `rootDir` is `src/`, so testable logic must not live in `prisma/`). Imported questions carry `externalId`/`source`/`language`/`questionPrompt`/`subjectAreaId` and enter with **`topicId: null`** (area only) and **`explanation: null`**; every consumer must tolerate both. Images are served by the backend at `/media/enem/` from `ENEM_MEDIA_DIR` (Docker: `/data/enem-media`, in the `enem-media` volume). `Alternative` has `letter`/`position`/`imageUrl` — always select alternatives via `src/questions/question.select.ts` so the `orderBy: position` is never forgotten. The import must **never** run inside `seed.ts` (the e2e setup runs the seed on every suite). Generic AI provider layer: `src/common/ai/` (`completeJson` + provider selection by `AI_PROVIDER` or auto-detection); on-demand explanations (`POST /questions/:id/explanation`) and topic classification (`prisma/classify-questions.ts`) all go through it. Simulations sample by stratum (`src/common/sampling.ts`) instead of loading the whole pool; TRI score stays `null` whenever a simulado includes an uncalibrated (official) question. Each dataset folder is one application: the slug suffix sets `ExamYear.kind` (`examKind` in `mapping.ts`: `-reaplicacao` REAPLICACAO, `-segunda-aplicacao`, `-terceira-aplicacao`, `-digital`, `-belem` REGIONAL; none = REGULAR), the label and the code letter (`ENEM-2014T-136`); `isReapplication` stays true only for REAPLICACAO. On first container start `prisma/bootstrap.ts` runs seed + import + keyword classification + flashcards when the bank has no official questions (`AUTO_IMPORT=0` turns it off). The Docker image prunes dev deps (no ts-node), so `npm run build:scripts` compiles `prisma/*.ts` to `dist-scripts/` (`tsconfig.scripts.json`) and the container runs them with `node`; a script that reads a data file next to it must have that file copied in `build:scripts`. **ENEM de 1998 a 2008** (`isSingleBookletExam`): prova única de 63 questões interdisciplinares, um dia, 5h — um simulado só (`examDays`) e a tela mostra "Prova única". O INEP não dá área a essas questões (o dataset traz `discipline: null`); a área vem de `src/common/enem-import/legacy-areas.ts`, **classificação do OpENEM pelo conteúdo, não oficial** (`areaClassified` no import), e questão fora dele entra sem área. Reimportar não apaga área/assunto de uma questão sem área no mapeamento. O gabarito dessas provas e da PPL 2010/2011 sai dos microdados do INEP (`tools/enem-fix/gabaritos-antigos.mjs`).

**Conserto do dataset (`tools/enem-fix/`):** o dataset do `updated-enem-api` veio de uma extração de PDF e traz defeitos — questões sem o texto das alternativas (quase toda a reaplicação de 2017/2020/2021/2025), enunciado ilegível em 2017 e 2021 (fonte sem mapeamento para Unicode), fórmula virada texto solto, gabarito de espanhol repetindo o do inglês e questões que faltam. A ferramenta refaz essas questões a partir dos cadernos oficiais do INEP: `parse.mjs` lê o caderno por coordenadas, o que não vira texto limpo é recortado como imagem e `gabarito.mjs` lê a resposta pela posição na página (o texto linearizado erra — em 2015 as colunas estão desalinhadas e em 2009 há quatro cadernos lado a lado). Duas travas evitam casar questão errada: a numeração do caderno é conferida contra o dataset, e o gabarito oficial só substitui o do dataset quando concorda com ele em ≥90% da prova. Provas que o dataset não tem (reaplicações 2012–2016, 3ª aplicação 2014, 2ª aplicação 2016, ENEM Digital 2020–2022, Belém 2025) são montadas do zero por `criar.mjs` a partir de `provas-novas.json`; `--comparar` valida o extrator refazendo uma prova que o dataset já tem. PPL 2010/2011 e ENEM 1998–2008 ficam fora: o INEP não publica gabarito. O resultado **não é versionado aqui** (o dataset é GPL-2.0): ele vai para o `updated-enem-api`, senão `db:import:enem --refresh` apaga tudo. Ver `tools/enem-fix/README.md`.

**LGPD e documentos legais:** o cadastro exige `acceptTerms: true` e grava `User.termsAcceptedAt`/`termsVersion` (`TERMS_VERSION` em `src/common/terms.ts`, igual ao cabeçalho `atualizado` das páginas legais; `openem_site/src/legal/documentos.test.ts` cobra). `GET /users/me/export` devolve um JSON com tudo do aluno (`src/users/data-export.ts`: o teste compara `EXPORT_SELECT` com as relações de `User` no DMMF, então tabela nova ligada ao aluno tem de entrar lá; `passwordHash` nunca sai) e `DELETE /users/me` pede a senha atual (errada é 403, não 401, e conta no limite por conta do login), desconta curtidas/votos dados e apaga o usuário (o cascade leva o resto). O `JwtStrategy` confere se o usuário existe: token de conta excluída vira 401. No fórum, `DELETE` do próprio tópico/resposta (do outro é 404) e `POST .../report` gravam em `ForumReport` (sem tela de moderação; ver docs hospedar/produção). O Perfil tem "Baixar meus dados" e "Excluir conta" (`src/components/MeusDados.tsx`; depois de excluir, `src/lib/conta.ts` limpa token, `api-cache` e o IndexedDB `openem`), e a exportação fica fora do cache do service worker. As páginas `/privacidade/` e `/termos/` (e `/en/...`) moram em `openem_site/src/legal/conteudo/`, com `[PLACEHOLDER]` para quem hospeda preencher.

Remaining work: native apps (React Native/Expo) are **out of scope for now** — see `docs/PRD.md` §18. The full application plan (data model, Docker Compose, CI/CD, testing strategy, and phased roadmap) lives in `docs/PRD.md` — consult it for product/architecture decisions before adding domain modules. Target-audience research is in `references/` (gitignored).

The primary language for documentation and API content is **Portuguese**. English mirrors of the docs live in `.github/docs/` (e.g. `README-EN.md`, `CONTRIBUTING-EN.md`, `SECURITY-EN.md`); keep both in sync when editing docs.

## Layout

- `openem_backend/` — NestJS API + Prisma. Run all npm/nest/prisma commands from here.
- `openem_frontend/` — React + Vite + Tailwind (v4) PWA. Run frontend commands from here.
- `openem_site/` — site público, separado do app (issues #88 e #89): landing em `/` e documentação em `/docs/`, em React + Vite, pré-renderizados em HTML estático no build (`scripts/prerender.mjs` + `src/entry-server.tsx`; cada página tem a sua entrada, a landing não carrega o roteador). A estética é a do app por construção: o site importa `openem_frontend/src/index.css` (tokens, temas, `.card`/`.btn`…) e serve `theme-boot.js` e `icon.svg` direto de `openem_frontend/public`; as fontes são self-hosted (fontsource). Os temas de redação vêm de `openem_frontend/src/data/redacoes.json` por um módulo virtual no build (`virtual:arquivo-redacoes`). A landing ("Treine com as questões que já caíram no ENEM.") tem na hero um caderno de prova interativo (`src/landing/Caderno.tsx`): escolher um ano de 1998 a 2025 troca a capa, com o formato da prova, as áreas de cada dia e o tema da redação regular. As regras de formato ficam em `src/landing/prova.ts` e **espelham o importador** (`examDays`/`areaBlocks` em `openem_backend/src/common/enem-import/mapping.ts`): mudou lá, muda aqui; `logica.test.ts` as trava. Depois vêm números, como funciona e recursos, redações, "no papel" (PDF e quadro da sala), código aberto (seção sempre em `default-dark` via `data-theme`) e o fechamento; temas de cor aparecem só como "temas customizáveis", sem nomes de família. A landing não usa capturas de tela. A documentação é Markdown em `src/docs/conteudo/<alunos|hospedar|contribuir>/NN-slug.md` (cabeçalho `titulo`/`descricao`, sem H1, URL `/docs/<grupo>/<slug>/`); `conteudo.test.ts` barra travessão, H1 e link interno quebrado. **Inglês (issue #89):** a tradução fica em `src/docs/conteudo/en/<grupo>/` com o mesmo nome de arquivo e sai em `/docs/en/<grupo>/<slug>/` (`src/docs/i18n.ts`: idioma pela URL, textos da interface, `urlNoIdioma`); página sem tradução aparece em português no endereço inglês com aviso (`espelhoEmIngles`). Hospedar e contribuir estão traduzidos (o teste cobra); os guias de aluno ficam em português. O prerender grava `<html lang>` e `hreflang` de cada página. **Referência da API:** `/docs/contribuir/api/` é gerada de `src/docs/api/openapi.json` por `openApiParaMarkdown` (`src/docs/api.ts`); o JSON sai do backend com `npm run openapi` (`openem_backend/scripts/gerar-openapi.ts`: Nest em modo preview, sem servidor, banco nem Redis; config compartilhada em `src/openapi.ts`), e o CI roda `npm run openapi -- --check`. Mudou rota ou DTO, regere e faça commit do JSON. `src/docs/variaveis.test.ts` cobra que toda variável dos `.env.example` (raiz e backend) apareça em `hospedar/02-variaveis.md`. O app tem o item **Ajuda** (sidebar e "Mais", `NavItem.href` para link fora do router) e um cartão no Perfil, apontando para `/docs/` (`src/lib/site.ts`, `VITE_DOCS_URL` no dev). **Onde cada coisa mora (issue #88):** um domínio e uma porta. O nginx da imagem do frontend (`openem_frontend/Dockerfile`, **contexto na raiz**, com `Dockerfile.dockerignore`) serve o site na raiz (`/`, `/docs/`) e o app em **`/app/`** (Vite `base: '/app/'`, `basename` no router, manifest com `start_url`/`scope` `/app/`, service worker em `/app/sw.js`). Caminho absoluto do app passa pela base: as figuras de redação usam `figura()` (`src/lib/redacoes.ts`), e a rota do Workbox tem o literal `/app/redacoes/` (a função vai para dentro do SW, onde a constante não existe). Os endereços antigos do app (`/questoes`, `/login`…) têm 301 para `/app/...` no nginx; `nginx-rotas.test.ts` cobra que toda rota do `App.tsx` esteja na lista. O `/sw.js` do site (`openem_site/public/sw.js`) é o **kill switch** do service worker antigo, que morava na raiz: ele apaga o precache da raiz, renova no cache HTTP os endereços antigos (a mesma lista do nginx, `sw-antigo.test.ts`), se desregistra e recarrega as abas. O HTML sai com `Cache-Control: no-cache` (map `$cache_do_html`). Cada lado tem a sua CSP: a do site é mais fechada (sem YouTube, `blob:` nem Google Fonts). SEO no build: `robots.txt` sempre (sem `/app/` e `/api/`), `sitemap.xml` e URLs absolutas no Open Graph só com `SITE_URL` (`src/seo.ts`; build arg da imagem). O CI tem o job `site` (lint, testes, build e `npm run check:links`, que confere os links internos do `dist/`). No dev o app abre em `http://localhost:5173/app/`, e `VITE_APP_URL` (`.env.development` do site) deve apontar para lá.
- Root `docker-compose.yml` orchestrates `db` (PostgreSQL 17, named volume `pg-data`, published only on `127.0.0.1`), `redis` (Valkey 8, the API cache: `requirepass`, `maxmemory` + `allkeys-lru`, no persistence, published only on `127.0.0.1`), `backend` and `frontend`. It reads the root `.env` (template: root `.env.example`); `POSTGRES_PASSWORD`, `REDIS_PASSWORD` and `JWT_SECRET` are required.

## Commands

Backend (run from `openem_backend/`):

```bash
npm install            # install dependencies
npm run start:dev      # run with watch/hot-reload
npm run start:prod     # run compiled build (node dist/main) — requires npm run build first
npm run build          # compile to dist/
npm run lint           # ESLint with --fix over {src,apps,libs,test}
npm run format         # Prettier over src and test
npm test               # Jest unit tests (*.spec.ts under src/)
npm run test:e2e       # e2e tests (drops/recreates the `test_e2e` schema in the DATABASE_URL Postgres, migrates, seeds)
npm run test:cov       # unit tests with coverage — FAILS below thresholds (issue #47)
npx prisma migrate dev # create/apply a migration against the dev Postgres (`docker compose up -d db` first)
npx prisma generate    # regenerate the Prisma client after editing schema.prisma
npm run db:seed        # seed demo data (prisma/seed.ts)
npm run db:import:enem # import official ENEM exams (downloads the dataset; run after db:seed)
npm run db:classify:keywords  # classificação de assunto por palavra-chave (sem IA)
npm run db:classify    # AI topic classification of imported questions (needs an AI provider)
npm run db:seed:flashcards  # sincroniza o catálogo de flashcards (cria decks novos e atualiza os existentes)
npm run openapi        # regera openem_site/src/docs/api/openapi.json (referência da API); --check só confere
npx jest -t "substring"               # run tests matching a name
```

Frontend (run from `openem_frontend/`):

```bash
npm install            # install dependencies
npm run dev            # Vite dev server (proxies /api, /health and /media to :3000)
npm run build          # typecheck + production build (generates the PWA service worker)
npm run preview        # serve the production build locally
npm test               # Vitest unit/component tests
npm run test:cov       # same with coverage — FAILS below thresholds (issue #47)
```

Site (run from `openem_site/`):

```bash
npm install            # install dependencies
npm run dev            # Vite on :5174 (landing em /, docs em /docs/)
npm run check:links    # depois do build: links internos do dist/
npm run build          # typecheck + build + SSR bundle + prerender de cada página em dist/
npm test               # Vitest (lógica da landing e conteúdo da documentação)
```

Coverage thresholds (issue #47, enforced in CI): new PRs must not reduce coverage below the floor — backend and frontend each run `npm run test:cov` in CI. Current floors: backend 40/35/40/40, frontend 25/20/18/25 (stmts/branches/funcs/lines); raise them gradually toward 80% as suites grow.

Mutation testing (issue #47, part 2): `npm run test:mutation` (Stryker) runs **locally, not in CI** (a full run takes 45–80 min per job; see the comments in `ci.yml`) — run it before PRs that touch domain logic. Both configs are **incremental** (`reports/stryker-incremental-*.json`: only new/changed mutants run). Break threshold: backend 30%, frontend 50% — mutate lists exclude bootstrap, DTOs, modules, visual-style catalogs (lib/areas, lib/gamification, theme, PDF drawing/themes, the keyword catalog) and the board (canvas, low logic value). Raise `break` gradually as suites improve.

Whole stack: `docker compose up --build` from the repo root.

## Runtime

- The app listens on `process.env.PORT ?? 3000` (`src/main.ts`).
- Domain endpoints are under the global prefix `api/v1`; `/` and `/health` are excluded from the prefix. Swagger UI is served at `/api` (with bearer auth) and the OpenAPI doc is built in `src/main.ts`.
- A global `ValidationPipe` (whitelist + transform) is enabled; use `class-validator` DTOs.
- `PrismaModule` is `@Global()` — inject `PrismaService` anywhere without re-importing.
- Config comes from `.env` via `@nestjs/config` (`DATABASE_URL`, `JWT_SECRET`, `JWT_EXPIRES_IN`, `PORT`, optional `REDIS_URL`); see `.env.example`. Never commit `.env`.
- Rate limiting counts by `req.ip`. Behind a reverse proxy set `TRUST_PROXY` to the number of proxies in front of the API (`src/common/trust-proxy.ts`; Docker Compose uses `1` for the frontend's nginx, which sends `X-Forwarded-For`). Without it every user shares the proxy's IP and one attacker can lock everyone out of login; never enable it without a proxy in front (clients would forge the header) — that is why Compose publishes port 3000 only on `127.0.0.1`. The default limit (`THROTTLE_TTL_MS`/`THROTTLE_LIMIT`, parsed to numbers by `src/common/throttle-config.ts` — a string TTL made blocks last forever) counts **per route**; expensive routes have their own `@Throttle`.
- **Distributed rate limiting (issue #87, `src/rate-limit/`):** two named throttlers, `burst` (20/s, `THROTTLE_BURST_*`) and `default` (100/min). The tracker (`tracker.ts`) is `user:<id>` when the request carries a **valid** JWT — the global ThrottlerGuard runs before `JwtAuthGuard`, so it verifies the token itself; an invalid/expired one counts as the IP — and `ip:<ip>` otherwise. Counters live in Redis through `RateThrottlerStorage` (one Lua script per hit: INCR + PEXPIRE + block, `CacheStore.rateHit`), falling back to process memory when Redis is down or absent (`FallbackCacheStore`) — limits never stop applying and never take the API down. Keys are `openem:v1:rl[:THROTTLE_KEY_PREFIX]:...`; under `NODE_ENV=test` each app gets a random prefix (e2e suites share one Redis in parallel), so a test that needs two instances to share counters passes `THROTTLE_KEY_PREFIX`. `AppThrottlerGuard` sends a standard `Retry-After` on every 429 (the stock guard names it `Retry-After-burst` for named throttlers) and the Portuguese `rateLimitMessage`. Login also has a **per-account** limit (`LoginAttemptsService`): 5 failures in 15 min (email normalized and hashed, counted even for unknown emails so blocks reveal nothing) block the account for 15 min, doubling per block within 24 h (cap 24 h); success clears failures. The frontend reads `Retry-After` (`src/lib/rate-limit.ts`, `HttpError.retryAfterSec`), Login shows a countdown, and `syncPending` waits and resends the same action on 429. The frontend nginx adds an edge `limit_req` on `/api/` (50 r/s, burst 200, JSON 429 with `Retry-After`; `src/nginx-rate-limit.test.ts`).

  | Route | Limit | Why |
  | --- | --- | --- |
  | any | 20/s + 100/min per user (IP without login) | burst + default; covers `POST /answers` and simulation `finish` |
  | `POST /auth/login` | 30/min per IP + 5 failures/15 min per account | classroom behind NAT; account takeover from many IPs |
  | `POST /auth/register` | 20/min per IP | argon2 per request, mass sign-up |
  | PDF (`PDF_THROTTLE`) | 10/min | CPU-heavy rendering queue |
  | `POST /questions/:id/explanation` | 10/min | paid AI call (plus the daily quota) |
  | forum thread/reply/report | 10/min | spam |
  | `GET /users/me/export` | 5/10 min | reads every student table |
  | `DELETE /users/me` | 5/min + login per-account limit | password guessing with a stolen token |
  | themes create/update | 20/min, 30/min | spam |

  `/health` and `/media/` only count in the default limit.
- **Cache (issue #86):** global `CacheModule` (`src/cache/`) with `CacheService` (`get`/`set`/`del`/`getOrSet`/`bump`/`lock`). With `REDIS_URL` it lives in Redis (shared across instances); without it, in process memory (dev, unit tests, single-instance self-host; a warning in production). Pure rules (key, TTL jitter, serialization) in `src/common/cache-keys.ts`. Invalidation is by **versioned namespace**: keys carry the `catalog` version (`openem:v1:catalog:<v>:...`) and `bump('catalog')` / `invalidateCatalogCache()` (`src/cache/catalog-invalidation.ts`, called at the end of `seed`, `db:import:enem` and every `db:classify*`) just increments it — no `SCAN`. In memory mode a script runs in another process and cannot reach the API's memory, so namespaced keys last at most 1 min there. Cached today: `GET /subjects`, `/questions/exams`, `/questions/facets` (per language), the question detail (deleted when an AI explanation is written) and the GitHub stars of Ferramentas. `getOrSet` is single-flight per process and does not store `undefined` (unknown ids do not fill the cache). A store error becomes a miss plus a warning at most once a minute; `/health` reports `redis: up|down|disabled` without changing `status`. The AI explanation takes a distributed lock (`SET NX PX`) so two instances never pay for the same question. **Never** put per-student data (favorites, grades, answers) under a shared key, and never cache simulation grading, answer keys, XP or AI quota. The leaderboard and public decks are not cached (they change through the API on every answer/vote).
- Paid AI calls (today, generated question explanations) also go through a per-student 24 h quota plus an optional global cap (`AiUsage` table, `src/ai-usage/`, pure logic in `src/common/ai-quota.ts`; env `AI_EXPLANATION_DAILY_LIMIT`, `AI_DAILY_LIMIT`). Call `AiUsageService.reserve()` before any new paid AI call that a student can trigger.
- The SPA's security headers (CSP, nosniff, frame denial) are set in `openem_frontend/nginx.conf` (`location /app/`; the public site at `location /` has its own, stricter CSP; the API gets helmet's). `src/nginx-csp.test.ts` ties the CSP to the code: a new external origin (player, font, script) must be added there.
- New feature modules are added to the `imports` array of `AppModule` (`src/app.module.ts`). Prefer the Nest CLI (`npx nest g module/controller/service <name>`).
- Prisma uses **v6** (pinned): the classic `url = env("DATABASE_URL")` datasource. Do not upgrade to Prisma 7 without migrating to its config-file/driver-adapter model.
- The database is **PostgreSQL** everywhere (dev, CI, e2e, production). Dev: `docker compose up -d db` and `DATABASE_URL=postgresql://openem:<POSTGRES_PASSWORD>@localhost:5432/openem?schema=public`. Migrations start from a single `init_postgres` base; the 31 SQLite-era migrations were deleted in the switch (they live in git history). Text search must use `mode: 'insensitive'` — Postgres `contains` is case-sensitive, unlike SQLite's LIKE. Avoid raw SQL (only the health `SELECT 1` and the e2e schema drop exist). Postgres also sorts NULL the other way round (first in `desc`, last in `asc`; SQLite did the opposite): on a nullable scalar use `{ sort, nulls }` (e.g. `EssayPrompt.year`); on a relation field Prisma has no `nulls`, so the question list puts exam-less questions first (none exist in the real bank). e2e suites pick questions via `test/seed-questions.ts` (`examSlug=2023`), never "the first one": the import/classification suites create and delete questions in parallel.
- e2e isolation: `src/common/test-database.ts` fixes the schema name `test_e2e`; `test/global-setup-e2e.ts` drops only that schema and runs `migrate deploy` + seed (not `migrate reset`, which Prisma blocks when an AI agent runs it). The import/classification scripts refuse to run against it (`isTestDatabaseUrl`). Unit tests never open a connection.
